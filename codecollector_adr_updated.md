# ADR по текущей архитектуре codecollector

## Назначение документа

Этот документ фиксирует **только актуальные архитектурные решения** по `codecollector`.

В документе:
- нет ссылок на старые варианты;
- нет описания отмененных решений;
- используются только текущие сущности, команды и режимы работы;
- оставлены только те направления развития, которые полезно сохранить как `TODO`.

---

## Общие правила для текущего набора ADR

- `codecollector` работает с **внешним каталогом проекта** и не становится владельцем исходного кода проекта.
- Основной режим работы — **полуавтоматический**: анализ, генерация и проверка выполняются автоматически, применение в основной проект остается отдельным явным шагом.
- Источником проектного поиска и индекса остаются текущие механизмы `codecollector`, PostgreSQL и pgvector.
- Рабочие копии, артефакты запусков и session metadata продолжают храниться в файловой системе.
- Для каждого проекта knowledge-артефакт хранится **внутри самого проекта**.
- На текущем этапе основными операциями изменения считаются:
  - `replace_symbol`
  - `insert_after_symbol`
- Требования не хранятся как отдельные долговременные сущности предметной области. Они живут в рамках session и pipeline run.
- Описание проекта и подключаемых reference library передается извне, а не читается из специальных файлов внутри проекта.
- `codegenerator` остается внешним генератором кода и тестов, который вызывается из `codecollector`.

# ADR-001. Проект регистрируется как ссылка на внешний каталог

## Статус
Принято.

## Контекст
`codecollector` должен работать параллельно с несколькими проектами и помнить настройки каждого проекта между вызовами CLI и будущего API.

Сам проект физически остается внешним каталогом, но системе нужно знать:
- где расположен проект;
- как он называется;
- какие у него настройки проверки;
- что исключать из индексации;
- какие reference library с ним связаны.

## Решение
Проект в системе — это **зарегистрированная ссылка на внешний каталог проекта** с сохраненной metadata.

Минимальный состав metadata проекта:
- `project_id`
- `project_name`
- `project_root`
- `languages`
- `verification_commands`
- `index_excludes`
- `reference_library_ids`
- `reference_library_paths`
- `status`
- `created_at`
- `updated_at`
- `knowledge_path`
- `knowledge_updated_at`

Поле `languages` хранится как список, даже если сейчас основной рабочий сценарий — Python.

Примеры:
- `["python"]`
- в будущем: `["python", "typescript"]`

## Что это дает
- можно работать с несколькими проектами параллельно;
- можно повторно использовать уже зарегистрированный проект без повторной передачи всех параметров;
- можно изолировать индексацию, knowledge, workspace и run artifacts по проектам.

## Текущее состояние
Реализованы:
- регистрация проекта;
- хранение project metadata;
- получение проекта по `project_id`;
- список проектов;
- удаление регистрации проекта;
- onboarding проекта.

## TODO
- HTTP API поверх текущего CLI/service слоя.

# ADR-002. Требования живут в рамках session и pipeline run

## Статус
Принято.

## Контекст
`codecollector` не является отдельной системой управления требованиями. Он получает change request, анализирует кодовую базу, выбирает target, генерирует изменение и проверяет результат.

## Решение
На текущем этапе `codecollector` **не хранит требования как отдельные долговременные сущности**.

Требование:
- приходит во входной вызов;
- нормализуется в `ChangeRequest`;
- сохраняется в metadata session;
- копируется в run artifacts;
- используется в analyze / generate / repair flow.

Минимальный состав входного требования:
- `title`
- `description`
- `constraints`

Дополнительно можно поддерживать:
- `notes`
- внешний идентификатор требования, если он приходит из внешней системы.

## Текущее состояние
Реализованы:
- сохранение входного требования внутри session metadata;
- использование change request в `sessions analyze`, `sessions generate`, `sessions repair` и `pipeline generate`.

## TODO
- формальный HTTP JSON-контракт для внешнего модуля требований.

# ADR-003. Session — основная единица пользовательского сценария

## Статус
Принято.

## Контекст
После появления session-based flow нужно было зафиксировать отдельную сущность, которая связывает:
- входное требование;
- рекомендуемый target;
- выбранный target;
- историю run;
- историю workspace.

## Решение
`session` — это логическая единица работы по одному change request или небольшому набору связанных требований.

Session хранит:
- `session_id`
- `project_id`
- `input_requirements`
- `requested_operation`
- `status`
- `created_at`
- `updated_at`
- `run_ids`
- `workspace_ids`
- `recommended_target`
- `selected_target`
- `last_run_id`
- `last_workspace_id`

## Текущая семантика статусов session

`session.status` должен отражать актуальное пользовательское состояние, а не только факт последнего запуска.

Используются, в частности, следующие состояния:

- `analyzed`
- `target_selected`
- `generated`
- `generated_test_verification_failed`
- `repair_verification_failed`
- `repair_no_effective_change`
- `repaired`
- `finalized`

Особый случай `generated_test_verification_failed` нужен для ситуации, когда основной код применен успешно, но verification не пройден только из-за ошибки в сгенерированном тесте.

## Семантика session
- `sessions analyze` создает session и предлагает `recommended_target`;
- `sessions select-target` фиксирует пользовательский выбор;
- `sessions generate` создает новый run внутри session;
- `sessions repair` создает новый run внутри session;
- `sessions finalize` завершает session и может удалить финальный workspace.

## Текущее состояние
Реализованы:
- `sessions analyze`
- `sessions select-target`
- `sessions generate`
- `sessions repair`
- `sessions get`
- `sessions list`
- `sessions delete`
- `sessions finalize`

## TODO
- явное отображение active run / active workspace в будущем HTTP API.

# ADR-004. Run — единица одного внешнего шага изменения

## Статус
Принято.

## Контекст
Внутри одной session может быть несколько запусков генерации и исправления. Нужно явно различать логическую session и конкретный run.

## Решение
`run` — это один завершенный внешний шаг изменения кода.

Примеры run:
- `generate`
- `repair`
- прямой `pipeline generate`

Run должен хранить:
- `run_id`
- `selected_target`
- `change_request`
- `requested_operation`
- телеметрию шагов pipeline;
- внешний вызов codegenerator;
- результаты проверки;
- `merge_plan`;
- ссылку на финальный workspace этого run.

## Важное правило
Снаружи значим только **финальный workspace run**.

Промежуточные workspace, которые появляются внутри одного run, считаются техническими и автоматически очищаются.

## Текущее состояние
Реализованы:
- `run_id` как основная единица диагностики;
- `PipelineRunResult` как основной итоговый payload;
- хранение run artifacts в `.runs`;
- сохранение ссылок на run внутри session;
- правило одного финального workspace на run.

## TODO
- отдельный HTTP query API по run.

# ADR-005. Workspace — staging-копия проекта для конкретного run

## Статус
Принято.

## Контекст
Генерация и repair не должны менять исходный проект напрямую. Для этого используется staging workspace.

## Решение
`workspace` — это рабочая копия проекта, в которой применяется generated artifact и выполняется проверка результата.

Workspace используется для:
- apply generated artifact;
- repair apply;
- apply generated test;
- diff;
- verification;
- ручного review перед переносом изменений в основной проект.

## Правила
- исходный проект не меняется автоматически после generate;
- apply в основной проект — это отдельный явный шаг;
- внутри одного run остается только один финальный workspace;
- промежуточные workspace удаляются автоматически;
- финальный workspace может быть удален при finalize session.

## Текущее состояние
Реализованы:
- создание staging workspace;
- diff по workspace;
- metadata workspace в рамках session/run;
- автоматическая очистка промежуточных workspace;
- команды `workspaces get`, `workspaces diff`, `workspaces apply`.

## TODO
- дополнительные query-операции через HTTP API;
- policy хранения старых workspace и run artifacts.

# ADR-006. Хранение разделено: индекс отдельно, артефакты отдельно

## Статус
Принято.

## Контекст
В системе уже есть два разных типа данных:
- поисковый и индексный слой;
- файловые рабочие артефакты.

## Решение
Сохраняется текущее разделение хранения.

### PostgreSQL / pgvector
Используются для:
- индекса проекта;
- search documents;
- графовых связей;
- semantic search;
- reference retrieval.

### Файловая система
Используется для:
- `.runs`
- `.workspaces`
- metadata проектов;
- metadata session;
- run artifacts;
- project-level `knowledge.yaml`.

## Почему это сохраняется
Такое разделение уже соответствует реальному устройству системы и остается простым в сопровождении:
- быстрый поиск и индексация остаются в БД;
- рабочие артефакты и трассировка остаются в файлах.

## Текущее состояние
Реализовано и используется в текущем рабочем контуре.

## TODO
- при необходимости позже ввести более формальную политику хранения старых артефактов.

# ADR-007. Onboarding проекта — отдельный обязательный pipeline

## Статус
Принято.

## Контекст
Перед полноценной работой с проектом нужно подготовить индекс, knowledge и reference context.

## Решение
Для проекта существует отдельный этап `onboard`.

Onboarding:
- проверяет доступность project root;
- строит или обновляет индекс;
- синхронизирует search/vector слой;
- индексирует reference library;
- создает или пересоздает `knowledge.yaml`;
- переводит проект в состояние готовности.

## Где хранится knowledge
`knowledge.yaml` хранится внутри проекта, например:
- `<project_root>/.codecollector/knowledge.yaml`

## Важное правило
На текущем этапе `knowledge.yaml` пересоздается целиком во время onboarding.

Это относится:
- к первичному onboarding;
- к повторному onboarding.

## Текущее состояние
Реализованы:
- `projects onboard`;
- пересборка индекса;
- пересоздание `knowledge.yaml`;
- сохранение `knowledge_path` и `knowledge_updated_at`.

## TODO
- автоматический повторный onboarding после apply в основной проект.

# ADR-008. Поиск и выбор target зависят от requested_operation

## Статус
Принято.

## Контекст
Один и тот же change request может требовать разного выбора target в зависимости от того, нужно заменить существующий symbol или вставить новый symbol рядом с существующим anchor.

## Решение
`requested_operation` является обязательной частью analyze/generate contract и влияет на выбор target.

На текущем этапе поддерживаются:
- `replace_symbol`
- `insert_after_symbol`

## Семантика операций

### `replace_symbol`
Используется, когда нужно заменить уже существующий symbol.

В этом случае target трактуется как symbol, который будет заменен.

### `insert_after_symbol`
Используется, когда нужно вставить новый symbol после существующего symbol-anchor.

В этом случае target трактуется как anchor, а не как symbol для замены.

## Правило для ranking
Для `insert_after_symbol` ranking должен предпочитать:
- declaration-style symbol;
- классы;
- модели;
- символы из domain/model модулей, если запрос говорит о dataclass/model/schema.

При этом ranking должен понижать service-layer entrypoints как менее удобные anchor для вставки новых символов.

## Текущее состояние
Реализованы:
- `requested_operation` в analyze и session metadata;
- operation-aware ranking для `insert_after_symbol`;
- использование operation в session flow и pipeline flow.

## TODO
- отдельная API-валидация совместимости `selected_target` и `requested_operation`.

# ADR-009. Полуавтоматический режим — основной режим работы

## Статус
Принято.

## Контекст
Нужен режим, в котором система помогает автоматизировать изменение кода, но ключевое решение о применении остается под контролем человека или внешнего управляющего слоя.

## Решение
Базовый режим работы `codecollector` — **полуавтоматический**.

Это означает:
- shortlist кандидатов строится автоматически;
- рекомендуемый target выбирается автоматически;
- generate, repair и generate-test выполняются автоматически как части pipeline;
- итоговое применение в основной проект остается отдельным явным действием.

## Следствия
- session и run должны сохранять достаточную телеметрию для review;
- `merge_plan` нужен как dry-run summary для человека;
- финальный workspace должен быть доступен для diff и ручной проверки.

## Текущее состояние
Реализовано:
- session-based flow;
- прямой pipeline flow;
- diff и verification на финальном workspace;
- dry-run `merge_plan`.

## TODO
- отдельный внешний шаг `generate-test`, если он понадобится как ручная операция;
- более формальная модель ручных повторных шагов в HTTP API.

# ADR-010. Применение изменений в основной проект выполняется отдельно

## Статус
Принято.

## Контекст
Сейчас generate и repair работают в staging workspace. Нужно явно зафиксировать, что основной проект не должен меняться автоматически после генерации.

## Решение
Перенос изменений из workspace в основной проект выполняется **только отдельным явным шагом**.

Для apply используется:
- финальный workspace последнего успешного run.

Нельзя использовать:
- промежуточный workspace;
- устаревший workspace от старого run;
- технический workspace, который не является финальным состоянием run.

## После apply
После успешного применения:
- основной проект считается измененным;
- индекс и knowledge могут устареть;
- проект нужно переиндексировать повторным onboarding.

## Текущее состояние
Реализованы:
- `workspaces apply`;
- сохранение финального `last_workspace_id`;
- verification и merge dry-run на финальном состоянии.

## TODO
- защита от apply из неактуального workspace;
- автоматический repeat onboarding после apply.

# ADR-011. Reference library остаются отдельным входом и отдельным индексом

## Статус
Принято.

## Контекст
`codecollector` использует дополнительные reference artifacts при генерации и repair. Эти данные нельзя смешивать с кодом целевого проекта.

## Решение
Reference library рассматриваются как отдельный входной слой.

Они:
- регистрируются отдельно от проекта;
- индексируются отдельно;
- используются как reference context;
- подключаются к проекту через project metadata.

## Для reference library сохраняется
- идентификатор;
- имя;
- путь;
- языки;
- тип;
- статус;
- время создания и обновления.

## Текущее состояние
Реализованы:
- reference library indexing;
- reference retrieval в generation flow;
- передача reference context в `codegenerator`.

## TODO
- полноценный registry library как завершенный внешний контракт;
- отдельные query-операции по library через HTTP API.

# ADR-012. Источник project metadata и library metadata — внешний ввод

## Статус
Принято.

## Контекст
Нужно было явно определить, где берется описание проекта и подключаемых библиотек.

## Решение
На текущем этапе metadata проекта и reference library приходит **извне**:
- через CLI;
- в будущем через HTTP API.

Система не читает специальные файлы описания:
- внутри проекта;
- внутри reference library.

## Почему это решение сохраняется
Такой подход проще и надежнее для текущего этапа:
- не нужно поддерживать несколько параллельных источников истины;
- вся регистрационная metadata контролируется явным внешним вызовом.

## Текущее состояние
Реализовано для project registration.

## TODO
- довести до такого же явного и законченного контракта lifecycle reference library.

# ADR-013. Главный диагностический объект — PipelineRunResult

## Статус
Принято.

## Контекст
Результат generate/repair не должен сводиться к одному boolean. Для review, UI и диагностики нужен подробный объект с телеметрией.

## Решение
Главным итоговым объектом pipeline считается `PipelineRunResult`.

Он включает:
- `run_id`
- `change_request`
- `selected_target`
- `build_report`
- `steps`
- `search_candidates`
- `context_pack`
- `external_code_generation`
- `external_test_generation`
- `repair_generation`
- `generated_test_apply`
- `verification_report`
- `apply_result`
- `merge_plan`

Дополнительно рядом с полным `PipelineRunResult` используется отдельный краткий объект `ResultSummary`.

Он нужен для:
- CLI-ответов верхнего уровня;
- session-based flow;
- будущего UI и HTTP API.

`ResultSummary` содержит компактное итоговое состояние run без необходимости сразу читать весь подробный payload.

## Почему это важно
Именно этот объект позволяет:
- показать пользователю, что происходило в pipeline;
- отлаживать качество target selection;
- анализировать ошибки generation и test generation;
- строить UI без повторного чтения множества файлов вручную.

## Текущее состояние
Используется в `pipeline generate` и `sessions generate`.

## TODO
- отдельный HTTP read-model для run details.

# ADR-014. Verification выполняется на финальном состоянии run

## Статус
Принято.

## Контекст
Проверка результата должна выполняться не на промежуточных состояниях, а на том состоянии workspace, которое считается финальным для run.

## Решение
`verification_report` строится по финальному workspace run.

На текущем этапе в verification могут входить:
- `ast_parse`
- `py_compile`
- `pytest_recommended`
- дополнительные технические проверки

`failure_summary` должен отвечать на два вопроса:
- что именно упало;
- repairable ли этот результат.

При этом итоговый внешний статус run должен различать:

- общий сбой verification;
- сбой только сгенерированного теста.

Если verification не пройден только из-за generated test, используется отдельный статус `generated_test_verification_failed`.

## Текущее состояние
Реализовано и уже используется в generate flow.

## TODO
- при необходимости расширять набор проверок без усложнения базового контракта.

# ADR-015. Тестовая генерация остается частью generation flow, но не является основой архитектуры

## Статус
Принято.

## Контекст
Сейчас генерация тестов встроена в generation flow. При этом качество тестов ограничено качеством модели и доступным контекстом.

## Решение
Генерация тестов остается рабочей частью pipeline, но архитектурно система не завязана на то, что сгенерированный тест всегда будет корректным.

Важно следующее:
- основной код и generated tests рассматриваются отдельно в verification;
- падение только generated test фиксируется отдельным статусом `generated_test_verification_failed`;
- основной код в этом случае не отправляется в `repair`;
- сборка test prompt должна оставаться простой и поддерживаемой;
- оптимизация prompt не должна превращаться в сложную многоступенчатую систему.

## Практическое правило
На текущем этапе сохраняется баланс:
- структура prompt остается общей;
- example test source может использоваться как fallback;
- лишняя сложность не добавляется;
- дальнейшее существенное улучшение тестов откладывается до перехода на более мощные модели.

## Текущее состояние
Реализовано:
- отдельный вызов `generate-test`;
- включение generated test в финальный workspace run;
- раздельная диагностика code generation и test generation в run payload.

# ADR-016. Актуальное состояние документации должно описывать только текущее поведение

## Статус
Принято.

## Контекст
В рабочих README и ADR со временем накопились старые решения, временные оговорки и описания промежуточных состояний.

## Решение
Документация `codecollector` должна описывать только текущее состояние системы.

Это означает:
- не ссылаться на прошлые версии;
- не смешивать актуальную реализацию и старые планы;
- держать описание одной сущности в одном месте документа;
- оставлять только актуальные примеры;
- сохранять `TODO` только для действительно следующих шагов.

## Текущее состояние
Это правило применяется при актуализации README и ADR.

# Краткий итог

На текущем этапе `codecollector` — это система полуавтоматического изменения кода, которая:

- работает с зарегистрированными внешними проектами;
- подготавливает проект через onboarding;
- использует session-based и pipeline-based сценарии;
- различает `replace_symbol` и `insert_after_symbol`;
- выполняет generate и repair в staging workspace;
- хранит подробную телеметрию в `PipelineRunResult`;
- оставляет применение в основной проект отдельным явным действием;
- использует project knowledge, индекс и reference context как разные, но связанные слои.
