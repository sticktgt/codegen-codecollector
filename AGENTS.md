# Репозиторий codecollector

## Назначение
`codecollector` отвечает за:
- индексацию проекта,
- поиск релевантных символов,
- сбор контекста вокруг выбранной точки изменения,
- подбор reference artifacts,
- подготовку запросов для `codegenerator`,
- применение результата в staging workspace,
- верификацию кода и тестов,
- подготовку dry-run результата для ручного review.

## Что важно сохранять
- Простую и понятную orchestration-логику.
- Предсказуемое поведение CLI.
- Явное разделение этапов:
  - analyze / shortlist,
  - selection,
  - generation,
  - apply,
  - verification,
  - merge dry-run.
- Устойчивую структуру run artifacts.

## Подход к изменениям
- Не объединять несвязанные обязанности в одном сервисе.
- Не переносить бизнес-решения в низкоуровневые утилиты.
- Если меняется логика сборки контекста или prompt values, изменение должно быть локальным и объяснимым.
- Стараться сохранять совместимость существующих сценариев `pipeline` и `sessions`.

## Prompt assembly и test generation
- Логика сборки prompt-а должна оставаться простой.
- Не использовать сложные многошаговые эвристики урезания контекста.
- Урезание допустимо только если контекст реально превышает разумный лимит.
- Ничего не выбрасывать заранее без необходимости.
- Если есть example test source, он может использоваться как fallback или дополнительная опора, но не должен дублировать related tests и не должен доминировать над реальным контекстом проекта.
- Связность prompt-а важнее агрессивного уменьшения размера.

## Логирование
В логах должно быть видно:
- какой target выбран;
- какой operation используется;
- какие related tests переданы;
- есть ли example test source;
- использовался ли full file;
- какие части были урезаны;
- какой итоговый размер запроса собран;
- почему был выбран тот или иной режим.

Логирование должно помогать разбирать реальные ошибки генерации тестов и кода, а не только фиксировать факт вызова внешнего генератора.

## Верификация
- Структурные проверки должны оставаться обязательными.
- Отчёт о верификации должен быть понятен без чтения исходного кода.
- Если verification не пройден, пайплайн может выполнить `repair`, если ошибка считается исправимой.
- Если после всех проверок и попытки `repair` упал только сгенерированный тест, это должно ясно отражаться в результате.
- Нужно различать:
  - `verification_failed`
  - `generated_test_verification_failed`
- Это различие должно быть согласовано:
  - в `result_summary.status`;
  - в `session.status`;
  - в итоговом payload run;
  - в `merge_plan.summary_lines` и `impact.notes`.
- Не смешивать ошибку пользовательского кода и ошибку генерации теста.
- Не описывать основной production-код как некорректный, если проблема подтверждена только в generated test.

## Документация
При обновлении документации по `codecollector`:
- описывать только текущее состояние;
- использовать русские формулировки;
- сохранять цельные смысловые блоки;
- оставлять только актуальные примеры;
- явно описывать ограничения и TO DO, если они действительно актуальны.
- все статусы session и result summary должны быть описаны консистентно и в одном месте для каждой сущности.

## Что не надо делать
- Не усложнять prompt assembly ради одного кейса.
- Не размазывать одну и ту же логику по нескольким классам без причины.
- Не добавлять новые абстракции «на будущее», если они пока не дают реальной пользы.
- Не делать скрытых специальных случаев для конкретных demo-проектов.
