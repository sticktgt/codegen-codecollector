# Требования к описаниям в коде

Этот документ фиксирует минимальные требования к human-readable описаниям в Python-коде.

## Зачем это нужно

Индекс и поиск текущего runtime и ближайшего развития должны опираться в первую очередь на смысл, который уже живет рядом с кодом:
- module docstring;
- class docstring;
- docstring публичных функций и методов.

Это снижает зависимость от внешних эвристик и делает код самодокументируемым для человека, индекса и будущих этапов пайплайна.

## Обязательные правила

1. Каждый production-модуль должен иметь module docstring из 1–2 предложений.
2. Каждый публичный class должен иметь class docstring.
3. Каждая публичная function/method должна иметь короткий docstring с ответом на вопрос "что делает".
4. Для service- и controller-методов docstring должен отражать бизнес-смысл, а не только механическую операцию.
5. Для приватных helper-ов и тривиальных `__init__` допускается отсутствие docstring, если смысл уже покрыт классом или модулем.

## Рекомендуемая форма docstring

- что делает сущность;
- что она читает/изменяет/возвращает;
- при необходимости — какой side effect или исключение важны для понимания.

## Пример для service-метода

```python
"""Назначает тикет агенту, сохраняет изменения и формирует текст уведомления."""
```

## Пример для controller-метода

```python
"""Назначает тикет агенту и возвращает компактный ответ API-уровня."""
```
