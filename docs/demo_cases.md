# Demo cases

В проекте используются два набора demo-cases:
- `tests/golden/demo_cases.yaml` — базовые исполняемые сценарии;
- `tests/golden/demo_cases_v2.yaml` — усиленные сценарии на основе **change request**, а не просто feature-like запросов.

Оба набора прогоняются через `tests/test_golden_cases.py` и используют тот же service layer, что и CLI/UI.

## Зачем нужен отдельный набор demo-cases

Он нужен сразу для трех вещей:
- для демонстрации возможностей PoC;
- для regression-проверки после изменений;
- для живой документации о том, как система должна себя вести.

## Что проверяют кейсы

### Search
Проверяется, что по change request система:
- строит shortlist;
- выдает ожидаемый primary target;
- включает в shortlist поддерживающие symbols.

### Context
Проверяется, что для выбранного target система:
- собирает соседние сущности;
- показывает inbound/outbound связи;
- находит прямые и косвенно связанные тесты;
- поднимает knowledge/requirment-слой.

### Apply
Проверяется, что после применения prepared artifact:
- workspace валиден;
- новый или измененный symbol попадает в индекс;
- impact summary показывает ожидаемые caller/test-связи;
- формируется список рекомендуемых тестов к прогону.

## Почему это golden-проверки

`golden` означает, что для сценария есть заранее зафиксированный эталон поведения.

У нас это не весь вывод целиком, а набор ожидаемых признаков, например:
- top-1 qualname;
- presence in top-N;
- expected related test;
- expected impacted caller;
- expected new symbol after apply.

## Почему это еще и документация

Потому что кейсы описывают не внутренние детали кода, а обещанное поведение системы:
- что должно найтись по change request;
- какой context должен быть собран;
- что должно произойти после apply;
- какие тесты должны быть рекомендованы.

Если golden-тест падает, это значит, что runtime перестал соответствовать этой спецификации.
