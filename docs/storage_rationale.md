# Почему индекс хранится в SQLite совместно с YAML

## Короткий ответ

Потому что в системе одновременно живут два разных типа знания:
- **структурные факты**, которые удобно получать автоматически из кода и быстро обновлять;
- **ручные смысловые сведения**, которые человеку важно видеть и править как обычный текст.

SQLite и YAML покрывают эти роли лучше, чем любой из вариантов по отдельности.

## Почему не только YAML

Если хранить все в YAML, быстро становятся неудобными:
- partial incremental indexing;
- точечное обновление измененных файлов;
- быстрый поиск по символам и связям;
- адресные выборки для context pack и impact summary.

YAML хорошо подходит для чтения человеком, но плохо подходит как операционная база индекса.

## Почему не только SQLite

Если хранить все только в SQLite, неудобно:
- просматривать и обсуждать ручные описания в git diff;
- править knowledge-слой без специального интерфейса;
- версионировать архитектурные заметки и requirement-links как обычные текстовые артефакты.

SQLite хорошо подходит для машинных фактов, но не так удобен для ручного проектного знания.

## Какой компромисс используется

- SQLite хранит автоматически извлеченные структурные факты.
- YAML хранит ручной knowledge-слой: descriptions, keywords, requirement-links, архитектурные связи.

Такой гибрид дает:
- быстрый runtime-поиск и переиндексацию;
- человекочитаемый слой знаний рядом с кодом;
- независимость ручных аннотаций от пересборки индекса.
