# Целевая графовая модель текущего runtime и ближайшего развития

## Почему графовая модель нужна уже сейчас

Даже если физическое хранилище пока остается SQLite, логическая модель уже должна быть графовой.
Это позволяет:
- не привязываться к плоской SQL-структуре на уровне домена;
- постепенно усиливать разбор кода без переписывания всей модели;
- позже при необходимости перейти на graph DB без смены смысловой схемы.

## Узлы (nodes)

- `file`
- `module`
- `class`
- `function`
- `method`
- `test_case`
- `requirement`
- `layer`

## Ребра (edges)

- `contains` — файл или модуль содержит сущность
- `imports` — модуль импортирует модуль или символ
- `calls` — функция/метод вызывает другой символ
- `covered_by_test` — test_case покрывает production symbol
- `belongs_to_layer` — сущность относится к архитектурному слою
- `implements_requirement` — symbol реализует requirement
- `exposed_by_controller` — сервисная операция доступна через controller/API

## Разрешенные и неразрешенные связи

Для текущего runtime и ближайшего развития нужно различать два состояния ребра:
- `target_node_id` — целевой узел разрешен точно;
- `target_ref` — известен только текстовый ref, но точная сущность пока не разрешена.

Это позволит постепенно усиливать resolution без потери уже извлеченной информации.

## Почему пока не graph DB

На текущем этапе SQLite достаточно, потому что:
- граф небольшой;
- PoC работает локально;
- важнее сначала стабилизировать extractor и доменную модель.

Graph DB можно рассматривать позже, если появятся:
- multi-hop запросы через несколько слоев;
- кросс-языковые связи;
- более тяжелая интерактивная работа именно с графом.
