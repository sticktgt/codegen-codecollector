# codecollector

`codecollector` — оркестратор управляемой доработки локального Python-проекта. Он регистрирует проект, строит индекс кода, анализирует запрос на изменение, собирает контекст для `codegenerator`, применяет результат генерации в рабочую область, выполняет проверки, запускает исправление при ошибках и готовит результат для ручного применения.

`codecollector` не является пользовательским интерфейсом и не генерирует код самостоятельно. Пользовательский интерфейс находится в `codeui`. Генерация производственного кода, тестов, исправлений и advisory-разборов выполняется в `codegenerator`.

## Назначение

`codecollector` используется для локального workflow изменения кода:

1. Подключить проект.
2. Построить индекс проекта.
3. Создать или получить запрос на изменение.
4. Проанализировать запрос.
5. Выбрать целевой символ или точку вставки.
6. Собрать контекст генерации.
7. Запустить генерацию через `codegenerator`.
8. Применить результат в staging workspace.
9. Выполнить проверки.
10. Запустить repair при блокирующих ошибках производственного кода.
11. Сгенерировать и проверить тест, если режим тестогенерации включён.
12. Подготовить план ручного применения workspace.
13. Применить выбранный workspace к основному проекту отдельной командой.

## Основные возможности

- Регистрация локальных проектов.
- Инкрементальная и полная переиндексация проекта.
- Построение графового индекса модулей, классов, функций и методов.
- Построение поисковых документов.
- Синхронизация векторного поиска.
- Создание и обновление `.codecollector/knowledge.yaml`.
- Обогащение knowledge по архитектурному документу при onboarding.
- Анализ запроса на изменение.
- Определение операции изменения.
- Выбор целевого символа или точки вставки.
- Сбор context pack для генератора.
- Формирование контекста контрактов, моделей и разрешённой поверхности вызовов.
- Вызов внешнего `codegenerator`.
- Применение code artifact в staging workspace.
- Статические проверки artifact и patch.
- Runtime-проверки: AST parse, compileall, рекомендованные команды.
- Repair производственного кода при блокирующих ошибках.
- Генерация и проверка generated test.
- Advisory review при ошибке generated test.
- Формирование merge plan.
- Применение workspace к основному проекту.
- Обновление traceability-связей требований и CR в `knowledge.yaml` после применения workspace.

## Основные сущности

### Проект

Проект — локальная папка с исходным кодом. При подключении ожидается структура:

```text
<input-root>/
  src/
  ARCHITECTURE.md
```

Поддерживается архитектурный файл с именем, заданным в конфигурации. Папка `src/` становится корнем индексируемого кода.

Один корень проекта регистрируется один раз. Повторная регистрация того же пути возвращает контролируемую ошибку с данными существующего проекта.

### Сессия

Сессия создаётся при анализе запроса. Она хранит исходный запрос, выбранный проект, результат анализа, рекомендованную цель, выбранную цель, связанные запуски и последнюю рабочую область.

### Запуск

Запуск создаётся при генерации. Он хранит запрос, выбранную цель, context pack, запросы и ответы `codegenerator`, отчёт проверок, результат repair, generated test, diff, merge plan и timeline шагов.

### Workspace

Workspace — копия проекта для проверки результата. Изменения сначала применяются только в workspace. Основной проект изменяется отдельной командой `workspaces apply`.

### Knowledge

`knowledge.yaml` хранится в проекте в папке `.codecollector/`. Файл содержит описание модулей и символов проекта:

```yaml
modules:
  common.constants:
    title: Глобальные константы
    description: Содержит константы приложения.
    layer: common
    requirements:
      - SN-01-000001
    change_requests:
      - id: CR-D19
        applied_at: "2026-06-11T08:39:25+00:00"

symbols:
  note.note_storage.NoteStorage.save:
    title: Сохранение заметки
    description: Сохраняет заметку в файловую систему.
    keywords:
      - save
    requirements:
      - SN-01-000006
    change_requests:
      - id: CR-D21
        applied_at: "2026-06-11T09:10:00+00:00"
```

`requirements` и `change_requests` сохраняют связи применённых workspace с требованиями и CR. При переиндексации эти поля сохраняются и не очищаются.

## Подключение проекта

```bash
python -m codecollector projects onboard \
  --input-root /path/to/project \
  --project-name example \
  --full
```

Во время подключения выполняются:

1. Регистрация проекта.
2. Построение графового индекса.
3. Построение поисковых документов.
4. Синхронизация векторного поиска.
5. Создание `knowledge.yaml`.
6. Обогащение knowledge по архитектурному документу, если он найден и не отключён.
7. Сохранение диагностики подключения.

Если архитектурный документ отсутствует, проект подключается без обогащения. Если обогащение найденного документа завершается ошибкой, подключение считается неуспешным, а регистрация и индексы откатываются.

## Переиндексация

```bash
python -m codecollector projects reindex --project-id <project_id>
```

Полная переиндексация:

```bash
python -m codecollector projects reindex --project-id <project_id> --full
```

Переиндексация обновляет графовый индекс, поисковые документы, векторный индекс и `knowledge.yaml`. Поля `requirements` и `change_requests` в `knowledge.yaml` сохраняются для существующих модулей и символов.

## Анализ запроса

```bash
python -m codecollector sessions analyze \
  --project-id <project_id> \
  --request-file request.json
```

Анализ выполняет:

1. Проверку качества запроса.
2. Определение операции изменения.
3. Определение области вставки.
4. Поиск кандидатов.
5. Переранжирование кандидатов.
6. Выбор цели или точки вставки.
7. Формирование краткого контекста.
8. Формирование подсказок по переиспользованию.

Пример запроса:

```json
{
  "title": "Добавить проверку имени файла заметки",
  "description": "Добавить в NoteStorage метод is_note_file_name, который возвращает true для имён с расширением .note.",
  "constraints": [
    "Это добавление нового метода внутри класса NoteStorage.",
    "Не менять существующие методы.",
    "Не подключать метод к UI."
  ]
}
```

Статусы качества запроса:

- `processable` — запрос можно выполнять;
- `uncertain` — требуется решение пользователя;
- `insufficient` — генерация заблокирована до уточнения запроса.

## Операции изменения

Поддерживаются операции:

- `replace_symbol` — замена существующего символа;
- `insert_after_symbol` — вставка нового символа после выбранной точки или внутрь выбранного класса.

Для `replace_symbol` выбранный символ является изменяемой целью.

Для `insert_after_symbol` выбранный символ может быть:

- anchor-символом для вставки после него;
- parent-классом для вставки метода в `class_body`;
- соседним символом внутри модуля для вставки в `module_body`.

Поддерживаемые области вставки:

- `module_body` — вставка top-level функции, класса или module-level значений;
- `class_body` — вставка метода внутрь класса.

## Context pack

Контекст генерации включает:

- целевой символ или точку вставки;
- файл цели;
- родительский qualname;
- структуру модуля;
- члены класса;
- методы того же класса;
- связанные производственные символы;
- связанные тесты;
- рекомендованные проверки;
- inbound и outbound связи;
- контекст контрактов;
- разрешённую поверхность вызовов;
- поверхности моделей;
- справочные артефакты;
- подсказки по переиспользованию.

Разрешённая поверхность вызовов строится консервативно. Методы зависимостей разрешаются только при видимом подтверждении в коде, индексе или контексте. Стандартная библиотека и операции стандартных типов не запрещаются, если они нужны для задачи и не добавляют внешних зависимостей.

## Цепочка выполнения

```bash
python -m codecollector sessions generate --session-id <session_id>
```

Цепочка выполняет:

1. Обновление индекса проекта.
2. Подбор или подтверждение primary target.
3. Сбор context pack.
4. Подбор reference artifacts.
5. Вызов `codegenerator generate`.
6. Статическую проверку code artifact.
7. Применение artifact в staging workspace.
8. Статическую проверку patch.
9. Repair производственного кода при блокирующих ошибках.
10. Повторное применение исправленного artifact.
11. Повторные проверки после repair.
12. Вызов `codegenerator generate-test`, если тестогенерация включена.
13. Статическую проверку generated test.
14. Проверку релевантности generated test.
15. Применение generated test в workspace.
16. Runtime-проверки проекта.
17. Advisory review при ошибке generated test.
18. Подготовку merge plan.

Generated test не является обязательным доказательством корректности производственного кода. Он проверяется отдельно и может быть исключён из применения.

## Repair производственного кода

Repair запускается при блокирующих ошибках производственного кода. В запрос repair передаются:

- предыдущий artifact;
- критическая диагностика;
- разрешённая поверхность вызовов;
- контекст контрактов;
- authoritative coordinates цели;
- исходный пользовательский запрос;
- operation, insert scope, parent qualname и expected new symbol kind.

Authoritative coordinates используются как источник координат цели для repair. Diagnostic metadata не заменяет эти координаты.

## Проверки

Основные блоки проверки:

- structural review;
- проверка неизвестных runtime-имён;
- проверка неизвестных атрибутов `self`;
- проверка сигнатур проектных контрактов;
- проверка import changes;
- проверка доступности импортов;
- проверка surface моделей;
- разбор AST;
- `compileall`;
- запуск рекомендованных команд;
- статическая проверка generated test;
- проверка релевантности generated test;
- advisory review generated test failure.

## План применения

Merge plan формируется в режиме ручной проверки. Он содержит:

- режим merge;
- workspace path;
- changed files;
- symbols in changed files;
- linked requirements;
- recommended tests;
- recommended test commands;
- excluded files;
- summary lines.

Статус `ready_for_merge_review` означает, что результат готов к ручной проверке. Он не означает автоматическое применение.

## Применение workspace

```bash
python -m codecollector workspaces apply --workspace-id <workspace_id>
```

Для записи traceability можно передать CR и требования:

```bash
python -m codecollector workspaces apply \
  --workspace-id <workspace_id> \
  --change-request-id CR-D17 \
  --requirement-id SN-01-000001 \
  --requirement-id SN-01-000006
```

Также поддерживается список требований через запятую:

```bash
python -m codecollector workspaces apply \
  --workspace-id <workspace_id> \
  --change-request-id CR-D17 \
  --requirement-ids SN-01-000001,SN-01-000006
```

После успешного применения выполняется переиндексация и обновление `knowledge.yaml`:

- для `replace_symbol` связь пишется на заменённый символ;
- для `insert_after_symbol` связь пишется на созданный символ, если он есть в `knowledge.yaml`;
- для module-level значений, которые не индексируются как symbols, связь пишется на модуль;
- тестовые symbols не участвуют в traceability.

Если CR или требования не переданы, применение workspace выполняется без обновления traceability.

- параметры поисковых документов;

## Ограничения и недоработки

- Основной поддерживаемый язык проекта — Python.
- UI находится в отдельном проекте `codeui`.
- Генерация кода выполняется внешним `codegenerator`.
- Решение о применении результата принимает пользователь.
- Связи требований и CR в `knowledge.yaml` создаются только после фактического `workspaces apply`.
- Гипотетические связи требований с кодом не сохраняются.
- Module-level значения пишутся на уровень модуля, если они не индексируются как symbols.
- Generated tests являются вспомогательными проверками и могут быть исключены из применения.
- Semantic checks покрывают только часть возможных ошибок Python-кода.
