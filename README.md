# codecollector

`codecollector` — проект для подготовки изменения кода по change request, подбора контекста по проекту, вызова внешнего `codegenerator`, применения результата в staging workspace и запуска проверок.

Проект ориентирован на локальные LLM и ограниченный контекст. Основной сценарий работы — точечное изменение уже существующего кода с контролем объема передаваемого контекста и с сохранением артефактов запуска для отладки.

## Текущая реализация

`codecollector` выполняет следующие задачи:

1. читает код проекта и обновляет индекс символов;
2. использует `knowledge.yaml` как человекочитаемое описание проекта;
3. ищет target-символ по change request;
4. собирает контекст для изменения;
5. подбирает reference-артефакты;
6. формирует структурированный запрос для внешнего генератора;
7. вызывает внешний `codegenerator`;
8. применяет результат в staging workspace;
9. при ошибке применения или проверки может вызывать `repair`;
10. отдельным шагом может запускать генерацию теста;
11. запускает проверки проекта;
12. формирует итоговый отчет по запуску пайплайна.

## Общая схема работы

Для типового `pipeline generate` используется следующий порядок шагов:

1. обновление индекса проекта;
2. обновление search documents и vector index, если изменился код проекта;
3. поиск кандидатов по change request;
4. сбор context pack для выбранного target;
5. подбор reference-артефактов;
6. отдельный вызов `codegenerator generate`;
7. применение сгенерированного кода в staging workspace;
8. при ошибке применения — отдельный вызов `codegenerator repair` и повторное применение;
9. если для target нет достаточного тестового покрытия — отдельный вызов `codegenerator generate-test`;
10. применение сгенерированного теста;
11. проверки проекта;
12. формирование dry-run merge plan и итогового отчета.

## Основные функциональные блоки

### Индекс проекта

Индекс проекта хранит техническое представление кода:

- модули;
- классы;
- функции и методы;
- диапазоны строк;
- docstring;
- связи между символами;
- search documents для semantic search.

Индекс используется для:

- поиска target-символов;
- построения графа входящих и исходящих связей;
- формирования context pack;
- impact analysis после применения изменения.

### `knowledge.yaml`

`knowledge.yaml` — человекочитаемый слой описания проекта рядом с кодом.

Он может содержать:

- названия и описания модулей;
- названия и описания важных символов;
- keywords;
- связь символов с требованиями;
- архитектурные слои;
- дополнительные понятные для поиска формулировки.

В текущем подходе `knowledge.yaml` рассматривается как полуавтоматический артефакт: он может быть подготовлен автоматически и затем доработан аналитиком вручную.

Использование `knowledge.yaml`:

- помогает semantic search лучше понимать назначение символов;
- помогает выбирать target по change request;
- помогает формировать человекочитаемое объяснение причин выбора symbol;
- дает дополнительный слой описания проекта помимо docstring и структуры кода.

### Semantic search и search documents

Для поиска по change request `codecollector` использует search documents — короткие текстовые представления символов.

Они включают:

- имя символа;
- docstring;
- описание из `knowledge.yaml`;
- связанные требования;
- часть контекста по модулю.

Search documents сохраняются в хранилище индекса и используются для semantic search.

### Reference Library

Reference Library — отдельный набор эталонных примеров и переиспользуемых компонентов, который не является частью проекта пользователя.

Она нужна как дополнительный источник контекста для генератора и как место хранения небольших готовых решений, шаблонов и примеров, которые можно адаптировать или переиспользовать.

В текущей реализации библиотека описывается через `reference_library/library.yaml` и файловые артефакты.

В ней можно хранить:

- шаблоны функций;
- переиспользуемые компоненты;
- reference implementation;
- небольшие полезные сниппеты;
- примеры локализации, форматирования и типовых паттернов;
- заготовки тестов или вспомогательных функций.

Для каждого артефакта можно задать, например:

- язык;
- тип артефакта;
- режим использования;
- источник;
- заголовок и описание;
- keywords;
- границы snippet.

Как Reference Library используется в пайплайне:

1. по change request и target подбираются кандидаты;
2. выбирается небольшой top-N набор;
3. каждый артефакт материализуется как `full_file` или `snippet`;
4. в generation request попадают только выбранные артефакты.

В текущем demo-наборе есть два основных варианта артефактов:

- `template` — шаблон, который нужно адаптировать под текущую задачу;
- `reusable_component` — готовый компонент, который можно использовать как источник кода или логики.

По режиму использования сейчас видны как минимум два варианта:

- `adapt` — пример для доработки под текущий change request;
- `reuse` — переиспользуемый кодовый блок.

### Staging workspace

Все применения артефактов выполняются не в исходном проекте, а в отдельном staging workspace.

Это позволяет:

- безопасно применить код;
- проверить синтаксис и тесты;
- пересчитать индекс по измененным файлам;
- получить diff и impact summary;
- подготовить dry-run merge plan.

## Как формируется контекст для LLM

### Общий принцип

`codecollector` собирает минимально достаточный контекст. Для локальных моделей важны не только абсолютный размер prompt, но и его сложность, поэтому большие комбинированные запросы разделены на отдельные вызовы.

Контекст собирается из нескольких источников:

- выбранный target-символ;
- краткая структура модуля;
- связанные тесты;
- выбранные reference-артефакты;
- описание из `knowledge.yaml`.

### Контекст для `generate`

В `codegenerator generate` передаются:

- `change_request`;
- `target`;
- `project_context.module_outline` — короткий список символов модуля;
- `project_context.target_symbol` — исходный код target-символа;
- `project_context.related_tests` — только связанные тесты, если они найдены;
- `reference_context` — только выбранные reference-артефакты.

В обычном режиме полный файл не передается.

### Контекст для `repair`

`repair` вызывается только когда уже есть артефакт, который нужно исправить:

- при ошибке применения;
- при repairable ошибке проверки.

В `repair` передаются:

- исходный `change_request`;
- `previous_artifact`;
- краткое описание ошибки;
- тот же target-контекст;
- reference-контекст в сокращенном виде.

### Контекст для `generate-test`

Генерация теста вынесена в отдельный вызов, чтобы не перегружать основной запрос генерации кода.

В `generate-test` передаются:

- `change_request`;
- `target`;
- target-символ;
- module outline;
- текущий reference-контекст;
- признак отсутствия связанных тестов.

### Метрики размера контекста

Перед каждым внешним вызовом `codecollector` пишет в лог и в request-пayload метрики размера контекста.

В текущем формате используются, например:

- `request_chars`;
- `target_source_chars`;
- `related_test_chars`;
- `reference_chars`;
- `request_chars_limit`.

Эти поля используются для контроля prompt budget и анализа запусков.

### Как контекст уменьшается

Если контекст становится слишком большим, `codecollector` уменьшает его за счет:

- отказа от передачи полного файла;
- ограничения числа reference-артефактов;
- передачи snippet вместо full file;
- передачи только связанных тестов;
- усечения длинных reference-артефактов.

## Проверки после применения

После применения артефакта `codecollector` запускает проверки проекта.

Сейчас используются:

- `ast_parse` — проверка синтаксической корректности Python-файлов;
- `py_compile` — запуск `python -m compileall .`;
- `pytest_recommended` — запуск рекомендованных тестов, если они есть.

Если был сгенерирован новый тест, он попадает в список рекомендуемых тестов и прогоняется в verification.

## Демонстрационный проект

В качестве demo-проекта используется `demo_projects/sample_python_app`.

Это небольшой Python-проект `support_app`, который нужен для демонстрации полного dry-run pipeline:

- поиска основного места изменения по `change_request`;
- ручного или автоматического выбора target;
- сборки context pack;
- вызова внешнего шага генерации;
- применения изменения в staging workspace;
- structural validation;
- impact summary;
- dry-run подготовки merge.

Структура demo-проекта включает:

- `support_app/api/controllers.py` — API-слой и точки входа use-case-ов;
- `support_app/services/ticket_service.py` — бизнес-логика по тикетам;
- `support_app/services/notification_service.py` — формирование уведомлений;
- `support_app/services/report_service.py` — отчетные функции и сводки;
- `support_app/storage/ticket_repository.py` — простой in-memory репозиторий;
- `support_app/domain/models.py` — модели предметной области;
- `tests/` — тесты, используемые как связанный контекст и как рекомендуемые сценарии для проверки.

Для demo-проекта рядом с кодом лежит `.codecollector/knowledge.yaml` с описанием модулей, символов, требований и архитектурных слоев.

В репозитории также есть связанные демонстрационные материалы:

- `demo_change_requests/` — примеры structured change request;
- `demo_artifacts/` — вспомогательные артефакты для демонстраций;
- `tests/golden/` — наборы проверочных сценариев.

## Контракт вызова внешнего `codegenerator`

Внешний генератор вызывается через файловый request и возвращает машинно-читаемый JSON-результат.

### Вызовы `codegenerator`

`codecollector` использует три режима внешнего вызова:

- `generate` — генерация production-кода;
- `generate-test` — генерация теста;
- `repair` — исправление ранее полученного артефакта.

### `GenerationRequest`

`GenerationRequest` используется для режимов `generate` и `generate-test`.

Основные поля:

- `request_id` — идентификатор запуска;
- `mode` — режим вызова;
- `change_request` — описание изменения;
- `target` — описание символа, который нужно изменить;
- `project_context` — контекст проекта;
- `reference_context` — выбранные reference-артефакты;
- `options` — опции генерации;
- `context_metrics` — метрики размера request.

В `change_request` используются поля:

- `title`;
- `description`;
- `constraints`;
- `notes`.

В `target` используются поля:

- `qualname`;
- `file_path`;
- `operation`.

В `project_context` используются поля:

- `module_outline`;
- `full_file_source`;
- `target_symbol`;
- `related_tests`;
- `recommended_tests`.

В `reference_context` используются поля:

- `reference_summary`;
- `reference_artifacts`.

### `RepairRequest`

`RepairRequest` используется для режима `repair`.

Основные поля:

- `request_id`;
- `mode`;
- `previous_generation_request_id`;
- `change_request`;
- `error_context`;
- `previous_artifact`;
- `project_context`;
- `reference_context`;
- `options`.

### `GenerationResult`

В ответ `codegenerator` возвращает JSON следующего вида:

- `request_id`;
- `status`;
- `code_artifact`;
- `test_artifact`;
- `planner_result`;
- `warnings`;
- `trace_path`;
- `error_type`;
- `message`.

## Структура проекта

Ниже перечислены основные части `codecollector`.

### `config.yaml`
Основная конфигурация проекта.

### `.runs/`
Артефакты выполненных запусков пайплайна.

### `demo_projects/sample_python_app/`
Демонстрационный Python-проект `support_app` для модификации и проверки пайплайна.

### `reference_library/`
Библиотека reference-артефактов для включения в generation context.

### `codecollector_ui/`
Streamlit UI для просмотра run artifacts.

### `codecollector/indexing/`
Работа с индексом проекта, search documents и хранилищем индекса.

### `codecollector/search/`
Поиск target-символов по change request.

### `codecollector/context/`
Сбор context pack для выбранного target.

### `codecollector/reference_library/`
Подбор и материализация reference-артефактов.

### `codecollector/external_codegen/`
Подготовка request-файлов и вызов внешнего `codegenerator`.

### `codecollector/patching/`
Применение code artifact и generated test artifact в staging workspace.

### `codecollector/validation/`
Синтаксические и тестовые проверки после применения.

### `codecollector/orchestration/`
Оркестрация шагов пайплайна и формирование итогового результата запуска.

### `codecollector/workspace/`
Работа со staging workspace.

### `codecollector/vector_search/`
Поддержка semantic search по search documents.

## Плановые изменения и следующие шаги

Возможные следующие направления развития:

- прием в работу нового проекта и подготовка его артефактов;
- полуавтоматическая подготовка `knowledge.yaml` с возможностью ручного редактирования;
- запуск пайплайнов из UI;
- расширение набора поддерживаемых языков и связанных механизмов индексации и проверки.
