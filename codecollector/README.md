# codecollector

`codecollector` — оркестратор для управляемой доработки локального Python-проекта. Он регистрирует проект, строит индекс кода, анализирует запрос на изменение, собирает контекст для `codegenerator`, применяет сгенерированный артефакт в рабочую область проверки, выполняет проверки, запускает исправление при ошибках и готовит результат для ручной проверки перед применением.

`codecollector` не является пользовательским интерфейсом и не генерирует код самостоятельно. Пользовательский интерфейс находится в `codeui`. Генерация кода, тестов и исправлений выполняется в `codegenerator`.

## Возможности

- Регистрация локальных проектов.
- Первичная индексация проекта из папки с `src/`.
- Переиндексация проекта.
- Построение графового индекса модулей, классов, функций и методов.
- Построение поисковых документов.
- Синхронизация векторного поиска.
- Создание и обогащение `.codecollector/knowledge.yaml`.
- Анализ запроса на изменение.
- Определение операции изменения.
- Выбор целевого символа или точки вставки.
- Сбор контекста для генератора.
- Формирование разрешённой поверхности вызовов.
- Формирование контекста контрактов и моделей.
- Вызов `codegenerator`.
- Применение артефакта в изолированную рабочую область.
- Статическая проверка сгенерированного кода.
- Проверка сигнатур проектных контрактов.
- Компиляция и запуск рекомендованных проверок.
- Запуск исправления для производственного кода при ошибках.
- Генерация и проверка сгенерированного теста.
- Рекомендательный разбор ошибки сгенерированного теста.
- Формирование плана ручного применения рабочей области.
- Применение выбранной рабочей области в основной проект после решения пользователя.

## Основные сущности

### Проект

Проект — локальная папка с исходным кодом. При подключении ожидается структура:

```text
<input-root>/
  src/
  ARCHITECTURE.md
```

Также поддерживается имя архитектурного файла, заданное в конфигурации. Папка `src/` становится корнем индексируемого кода.

Один корень проекта регистрируется один раз. Повторная регистрация того же пути возвращает контролируемую ошибку с данными существующего проекта.

### Сессия

Сессия создаётся при анализе запроса. Она хранит исходный запрос, выбранный проект, результат анализа, рекомендованную цель, выбранную цель, связанные запуски и последнюю рабочую область.

### Запуск

Запуск создаётся при генерации. Он хранит запрос, выбранную цель, контекст, запросы и ответы `codegenerator`, отчёт проверок, результат исправления, сгенерированный тест, diff, план применения и временную шкалу шагов.

### Рабочая область

Рабочая область — копия проекта для проверки результата. Изменения сначала применяются только в рабочую область. Основной проект изменяется отдельной командой применения после ручной проверки.

## Подключение проекта

```bash
python -m codecollector projects onboard \
  --input-root /path/to/project \
  --project-name example \
  --full
```

Во время подключения выполняются:

1. Регистрация проекта.
2. Построение графового индекса.
3. Построение поисковых документов.
4. Синхронизация векторного поиска.
5. Создание `knowledge.yaml`.
6. Обогащение knowledge по архитектурному документу, если он найден.
7. Сохранение диагностики подключения.

Если архитектурный документ отсутствует, проект подключается без обогащения. Если обогащение найденного документа завершается ошибкой, подключение считается неуспешным, а регистрация и индексы откатываются.

## Переиндексация

```bash
python -m codecollector projects reindex --project-id <project_id>
```

Полная переиндексация:

```bash
python -m codecollector projects reindex --project-id <project_id> --full
```

Обычная переиндексация выполняет инкрементальную сборку. Полный режим перестраивает графовый индекс. Векторный поиск синхронизируется при изменении поисковых документов.

## Анализ запроса

```bash
python -m codecollector sessions analyze \
  --project-id <project_id> \
  --request-file request.json
```

Анализ выполняет:

1. Проверку качества запроса.
2. Определение операции.
3. Определение области вставки.
4. Поиск кандидатов.
5. Переранжирование кандидатов.
6. Выбор цели или точки вставки.
7. Формирование краткого контекста.
8. Формирование подсказок по переиспользованию.

Пример запроса:

```json
{
  "title": "Сделать автосохранение безопасным",
  "description": "Заменить существующий метод auto_save так, чтобы он сохранял заметку только при наличии несохранённых изменений.",
  "constraints": [
    "Это замена существующего метода auto_save.",
    "Использовать существующий признак несохранённых изменений.",
    "Не добавлять новый метод."
  ]
}
```

Статусы качества запроса:

- `processable` — запрос можно выполнять;
- `uncertain` — требуется решение пользователя;
- `insufficient` — генерация заблокирована до уточнения запроса.

## Операции изменения

Поддерживаются операции:

- `replace_символ` — замена существующего символа;
- `insert_after_символ` — вставка нового символа после выбранной точки или внутрь выбранного класса.

Для `replace_символ` выбранный символ является изменяемой целью. Для `insert_after_символ` выбранный символ является точкой вставки или родительским контейнером.

## Контекст генерации

Контекст генерации включает:

- целевой символ или точку вставки;
- родительский символ;
- структуру модуля;
- члены класса;
- методы того же класса;
- связанные производственные символы;
- связанные тесты;
- рекомендованные проверки;
- входящие и исходящие связи;
- контекст контрактов;
- разрешённую поверхность вызовов;
- поверхности моделей;
- справочные артефакты;
- подсказки по переиспользованию.

Разрешённая поверхность вызовов строится консервативно. Методы зависимостей разрешаются только при видимом подтверждении в коде, индексе или контексте. Стандартная библиотека и обычные операции стандартных типов не запрещаются, если они нужны для задачи и не добавляют внешних зависимостей.

## Генерация и проверка

```bash
python -m codecollector sessions generate \
  --session-id <session_id>
```

Цепочка выполнения выполняет:

1. Сбор контекста.
2. Вызов `codegenerator generate`.
3. Применение артефакта в рабочую область.
4. Статические проверки.
5. Проверки во время выполнения.
6. Исправление производственного кода при ошибках.
7. Повторную проверку после исправления.
8. Генерацию теста.
9. Проверку сгенерированного теста.
10. Рекомендательный разбор ошибки теста при необходимости.
11. Формирование плана применения.

Сгенерированный тест не является обязательным доказательством корректности производственного кода. Он проходит отдельные проверки и может быть исключён из применения.

## Исправление производственного кода

Исправление запускается при блокирующих ошибках производственного кода. В запрос исправления передаются:

- предыдущий артефакт;
- критическая диагностика;
- разрешённая поверхность вызовов;
- контекст контрактов;
- координаты целевого символа;
- требования исходного запроса.

Координаты целевого символа передаются как authoritative data: операция, файл, qualname, область вставки, родительский qualname и ожидаемый тип нового символа.

## Проверки

Основные блоки проверки:

- статическая проверка артефакта;
- проверка неизвестных имён;
- проверка неизвестных атрибутов `self`;
- проверка вызовов проектных контрактов;
- проверка import changes;
- разбор AST;
- компиляция Python;
- запуск рекомендованных команд;
- статическая проверка сгенерированного теста;
- проверка релевантности сгенерированного теста;
- запуск рекомендованного теста.

## План применения

План применения формируется в режиме пробного запуска. Он содержит:

- идентификатор рабочей области;
- список изменённых файлов;
- список изменённых символов;
- связанные требования;
- рекомендованные проверки;
- исключённые файлы;
- краткое описание результата.

Статус `ready_for_применении_review` означает, что результат готов к ручной проверке. Он не означает автоматическое применение.

## Применение рабочей области

```bash
python -m codecollector workspaces apply --workspace-id <workspace_id>
```

Перед применением пользователь проверяет рабочую область, diff, изменённые файлы, исключённые файлы, рекомендованные проверки и итоговый статус запуска.

## Артефакты запуска

Артефакты сохраняются в `.runs`.

Основные файлы:

- `цепочку выполнения_run_*.json`;
- `generation_request.json`;
- `generation_result.json`;
- `repair_request.json`;
- `repair_result.json`;
- `generation_test_request.json`;
- `generation_test_result.json`;
- `generated_test_review_request.json`;
- `generated_test_review_result.json`;
- stdout и stderr внешних вызовов;
- трассировка `codegenerator`;
- отчёт проверок;
- план применения.

## Конфигурация

Основной файл настроек — `config.yaml`.

В конфигурации задаются:

- пути состояния, запусков и рабочих областей;
- параметры индексации;
- параметры поисковых документов;
- параметры векторного поиска;
- параметры справочной библиотеки;
- команды и лимит времени внешнего `codegenerator`;
- проверки во время выполнения;
- настройки сгенерированных тестов;
- лимиты контекста;
- параметры моделей и точки доступа.

## Проверки проекта

```bash
python -m compileall -q codecollector
python -m pytest -q
```

## Ограничения

- Основной поддерживаемый язык проекта — Python.
- Основная рабочая схема — один запрос на один основной символ.
- Многофайловая генерация не является основным режимом.
- Сгенерированные тесты проходят отдельную проверку и могут быть исключены.
- Подсказки по переиспользованию являются мягким контекстом, если они не переданы как обязательные контракты.
- Применение рабочей области требует ручного решения пользователя.
