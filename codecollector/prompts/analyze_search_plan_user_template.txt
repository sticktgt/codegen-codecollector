Сформируй компактный план анализа change request для codecollector.

Верни только валидный JSON без markdown.

JSON-формат ответа:
{
  "request_quality": {
    "status": "processable | uncertain | insufficient",
    "reason": "короткое объяснение",
    "missing_information": ["что нужно уточнить"]
  },
  "change_kind": {
    "value": "symbol_change | import_change | file_level_change | uncertain",
    "confidence": 0.0,
    "reason": "короткое объяснение"
  },
  "operation": {
    "value": "replace_symbol | insert_after_symbol | unknown",
    "confidence": 0.0,
    "reason": "короткое объяснение"
  },
  "insert_scope": {
    "value": "module_body | class_body | unknown",
    "confidence": 0.0,
    "reason": "короткое объяснение"
  },
  "expected_new_symbols": [
    {"name": "имя", "kind": "function | class | method | unknown"}
  ],
  "search_plan": {
    "search_queries": ["короткая поисковая фраза"],
    "preferred_files": ["path/to/file.py"],
    "preferred_qualnames": ["package.module.symbol"],
    "preferred_layers": ["domain | services | api | storage | tests"],
    "avoid_layers": ["слой"],
    "reason": "короткое объяснение"
  },
  "multi_target_likely": false,
  "manual_review_required": false,
  "warnings": []
}

Правила:
- Если user_operation задана человеком, верни ее как operation.value, но можешь добавить предупреждение в reason/warnings.
- Поле change_kind описывает тип изменения: symbol_change — замена или добавление функции/метода/класса; import_change — изменение способа подключения зависимости или пути import; file_level_change — изменение на уровне файла, которое не сводится к одному symbol; uncertain — тип изменения неясен.
- Если запрос описывает изменение способа подключения зависимости, import, пути модуля или ситуацию, когда установленный компонент не распознается приложением, используй change_kind="import_change" или change_kind="file_level_change". Не выбирай symbol_change только потому, что рядом есть метод, который использует это имя.
- Если change_kind="import_change" или change_kind="file_level_change" и в текущей схеме нет надежного symbol-target для такого изменения, используй operation.value="unknown" и manual_review_required=true.
- Если user_insert_scope задан человеком, верни его как insert_scope.value, но можешь добавить предупреждение в reason/warnings.
- Для replace_symbol ищем существующий symbol, который нужно заменить целиком.
- Если запрос звучит как «реализовать/дореализовать/заполнить» поведение, и в проекте уже есть существующий method/function stub с NotImplementedError/TODO, совпадающий по смыслу, предпочитай replace_symbol этого stub, а не insert_after_symbol.
- Для insert_after_symbol ищем anchor-symbol, после которого нужно добавить новый symbol; используй insert_after_symbol только когда нужно добавить новый API, а не заполнить существующую заглушку.
- Если пользователь просит добавить функцию/helper на уровне модуля, используй insert_scope=module_body и expected_new_symbols.kind=function.
- Если пользователь явно просит добавить метод в класс, используй insert_scope=class_body и expected_new_symbols.kind=method.
- Если пользователь использует слово "функция" в смысле новой возможности/обработчика, но в project_map похожий слой реализован методами класса/controller, предпочитай insert_scope=class_body и expected_new_symbols.kind=method.
- Если непонятно, функция это или метод класса, используй insert_scope=unknown и manual_review_required=true.
- search_queries должны быть короткими: 2-5 слов, максимум 4 запроса.
- project_map может быть неполным: отсутствие symbol в нем не доказывает отсутствие в проекте.
- Если пользователь явно назвал symbol, добавь его короткое имя в search_queries; preferred_files и preferred_qualnames заполняй только надежными значениями.
